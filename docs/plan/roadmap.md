# План: shared-пакет, NestJS, вход по логину, браузер для Claude

Четыре первоочередные задачи и порядок, в котором их проще делать.

| # | Задача |
|---|---|
| 1 | Пакет `shared/` с общими модулями и типами для bot и webapp |
| 2 | Перевод бэкенда (`bot/src/server/`, Hono) на NestJS |
| 3 | Необязательная авторизация через Telegram: в Mini App — автоматически по initData, в браузере — логин/пароль, с возможностью связать аккаунт с Telegram |
| 4 | Возможность для Claude смотреть приложение в браузере через MCP |

## Порядок

**Шаг 0 (часть задачи 4) → 1 → 2 → 3 → 4 (полностью).**

Ключевая зависимость: авторизацию (3) делаем **после** переезда на NestJS (2) — иначе её придётся
писать дважды (сначала на Hono, потом переносить в guards Nest).

## Шаг 0 — Claude смотрит приложение локально (часть задачи 4) ✅

**Готово:** у Claude свой dev-пользователь `DEV_USER_ID=-1000000001` (отрицательный — не пересекается
с Telegram id, данные владельца не видны), браузер — Playwright MCP (`claude mcp add playwright`,
локально у разработчика), вывод в `.playwright-mcp/` (в `.gitignore`). Webapp вне Telegram стартует:
SDK пропускает инициализацию с предупреждением, API отвечает от имени dev-пользователя.
При выдаче id браузерным пользователям (шаг 3) не занимать `-1000000001`.

Отдельная авторизация для этого не нужна: в `bot/src/server/middleware/initData.ts` уже есть
dev-обход — при заданном `DEV_USER_ID` (`config.devUserId`) запрос без подписи Telegram пропускается
от имени этого пользователя.

- Запуск `yarn dev:all` с `DEV_USER_ID` в `bot/.env`, Vite открывается в обычном браузере.
- Подключение браузерного MCP (`claude-in-chrome` уже доступен, альтернатива — Playwright MCP).
- Проверить, что webapp вне Telegram стартует без ошибок (`init.ts` — защищённая инициализация SDK).

**Почему первым:** дёшево и окупается на всех следующих шагах — особенно при переезде на NestJS,
где после каждого перенесённого раздела экраны можно прокликать и поймать регрессии.

**Ограничение:** dev-базы нет — в браузере работаем с прод-данными пользователя `DEV_USER_ID`.

## Шаг 1 — пакет `shared/` ✅ (каркас)

**Готово:** workspace `shared/` (`@tg-rp-bot/shared`), собирается в `dist/` и подключается bot и webapp;
корневые скрипты и Dockerfile собирают его первым. Перенесены контракты персонажей, персон, пресетов, RP- и narrator-шаблонов
(`*Input`, `*ListItem`) и их лимиты — дубли в bot и webapp удалены. Остальные домены переносим по
мере надобности (в первую очередь — при переезде соответствующего раздела на NestJS). Устройство —
[docs/architecture.md](../architecture.md).

Небольшой и почти безрисковый шаг. Главная цель — описать **типы запросов/ответов API** в одном месте
до переезда на NestJS: контроллеры Nest сразу пишутся под них, webapp использует их же вместо копий.

- Резолв: пакет собирается `tsc` (`nodenext`) в `dist/`, bot (`nodenext`) и webapp (`bundler`) читают
  собранный `dist` — исходники напрямую не подходят (`rootDir` бота, прод исполняет только `.js`).
- Начать только с типов (и, возможно, zod-схем валидации); общую логику переносить потом, по мере надобности.

## Шаг 2 — бэкенд на NestJS

Самая крупная задача: `bot/src/server/` — около 6 500 строк в 102 файлах.

**Цель — не просто перенести маршруты, а привести бэкенд к строгой архитектуре Nest** (модуль /
контроллер / сервис / репозиторий / DTO, предсказуемые папки и файлы). Переписывать текущий код под
эту архитектуру можно и нужно — небольшими блоками, каждый с тестами, прод работает между блоками.

**Образец** — `D:\GitProject\dnd-online` (`apps/server`): тот же стек (Nest 12, нативный ESM `nodenext`,
Express, Drizzle, pino, `shared/dist`), там рецепт сборки уже проверен:
- сборка и dev — Nest CLI (`nest build` / `nest start --watch`, под капотом `tsc` с
  `emitDecoratorMetadata`); `tsx`/esbuild метаданные декораторов не генерирует — DI получил бы `undefined`;
- тесты — в dnd-online vitest + `unplugin-swc` (esbuild тоже не генерирует метаданные). У нас пока не нужен:
  сервисы в тестах создаются напрямую с моком репозитория, без DI-контейнера. Подключить, когда
  понадобится `@nestjs/testing` (e2e модуля);
- валидация — DTO на `class-validator` + глобальный `ValidationPipe({ whitelist, transform })`;
  DTO-класс `implements` тип контракта из `@tg-rp-bot/shared`;
- логи — `nestjs-pino` поверх нашего pino-логгера; правила логирования из CLAUDE.md не меняются.

### Раскладка (как в dnd-online)
Доменный модуль Nest — папка `bot/src/<домен>/`: `<домен>.module.ts`, `.controller.ts`, `.service.ts`,
`.repository.ts` (доступ к БД, бывший DAO из `db/<домен>/`), `dto/`, тесты рядом. Общее —
`bot/src/database/` (`DatabaseService` поверх текущего drizzle-клиента), `bot/src/auth/` (guard,
`@CurrentUser()`). Перенесённый домен удаляется из `server/` и `db/`; когда `server/` опустеет — Hono уходит.

### Переносить постепенно
Nest поднимается на том же порту, текущее Hono-приложение подключено за ним через `getRequestListener`
(`@hono/node-server`). Express-middleware без пути, до body-parser Nest, отдаёт в Hono всё, что не
входит в явный список перенесённых префиксов (`/api/characters`, …) — включая статику Mini App и SSE.
- **Блок A ✅** — каркас: Nest + мост в Hono, поведение не меняется.
- **Блок B ✅** — characters (модуль/контроллер/сервис/репозиторий/DTO) + общие auth/ database/ users/
  common/. Проверено: тесты, браузер (создание/правка/удаление с фото ~1 МБ), Docker-образ.
- **Блок C ✅** — personas по тому же шаблону; общий декоратор поля-картинки `IsDataImageUrl` и
  `found()` вынесены в `common/`.
- **Блок D ✅** — presets: контракт (PresetInput, уровни рассуждения, SamplingKey) перенесён в
  shared, валидация сэмплинга — декораторами DTO по SAMPLING_RANGES.
- **Блок E ✅** — rp-templates: контракт и набор компонентов промпта (PROMPT_COMPONENT_IDS) — в
  shared; вес шаблона в токенах считает сервис, тексты промптов в список не уходят.
- **Блок F ✅** — narrator-templates: контракт, дефолтный порядок narrator-промптов и уровни
  рассуждения перевода — в shared; порядок по-прежнему нормализуется (без 400).
- **Блок G ✅** — cards, CRUD: контракт (форма, категории и ask_user, лимиты, дефолты новой карточки) —
  в shared; весь `/api/cards` в Nest, ручки генерации пока делегируют в legacy `server/cards/generation/`
  через тот же лок карточки.
- **Блок H** — генерация карточек: перенос `server/cards/generation/` в Nest-сервис (DI вместо мостов
  `db/cards`, `db/presets`).
- **Дальше** — остальные домены по одному (… chats/stories с SSE
  последними), затем бот grammY как provider и удаление Hono.

### Контракт ответов не меняется
webapp (`apiFetch`) читает тело любого успешного ответа как JSON и текст ошибки из `message ?? error`:
- коды и тела ответов — как в Hono (`201 {character}`, `200 {ok:true}`, без `204`);
- глобальный exception filter отдаёт `{ error: string }` (сообщение `ValidationPipe` — массив, его
  склеиваем), неожиданные ошибки логирует `logger.error` с контекстом запроса;
- лимит JSON-тела задаётся явно: по умолчанию в Express 100 КБ, а картинки персонажа — до ~3,4 МБ.

### Подготовить почву для авторизации
Сейчас текущий пользователь Telegram (`c.get("tgUser")`) читается в 26 файлах, 118 раз. При переносе
заменяем это на декоратор `@CurrentUser()`, который отдаёт **внутренний `userId`**, а не объект
пользователя Telegram. Тогда в шаге 3 достаточно добавить второй guard — контроллеры не трогаем.
- Проверка initData (включая dev-обход и тексты 401) — одна чистая функция, её вызывают и
  Hono-middleware, и guard Nest.
- `ensureUser` (строка в `users` для FK) делает guard с кэшем на процесс, а не каждый контроллер.

### Без проблем переносятся
- SSE-стриминг генерации — через `@Sse` или сырой ответ.
- Бот grammY — как отдельный сервис (provider) внутри приложения Nest.
- Раздача статики Mini App — `@nestjs/serve-static` (только если `public` существует, исключая
  `/api/{*path}`) или сырой обработчик с SPA-fallback.

### Осторожно
- **helmet с настройками по умолчанию ломает Mini App в Telegram Web**: `X-Frame-Options: SAMEORIGIN`
  и CSP `frame-ancestors 'self'` запрещают показ во iframe. Если подключать — отключить эти заголовки
  или разрешить домены Telegram.
- `verbatimModuleSyntax`: класс, внедряемый через DI или указанный в декорированной сигнатуре,
  импортируется как значение, не `import type` — иначе пропадут метаданные.

## Шаг 3 — вход по логину и паролю

Главная сложность — не Nest, а схема данных:
- **`users.id` сейчас равен Telegram user id**, на него ссылаются 10 внешних ключей.
- **Ключ шифрования данных пользователя выводится из `users.id`** (`getUserEncryptionKey` в
  `bot/src/utils/crypto.ts`, HKDF от мастер-ключа). Значит, id пользователя **нельзя менять никогда** —
  иначе его зашифрованные данные станут нечитаемыми.

### Схема
- Существующие пользователи сохраняют свой id.
- Пользователям, зарегистрированным через браузер, выдаём id из диапазона, не пересекающегося с
  Telegram (например, отрицательные числа или отдельная последовательность).
- Логин, хэш пароля и привязанный Telegram id — в отдельной таблице идентичностей.
- Сессия в браузере — cookie/JWT; в Mini App по-прежнему подписанный initData. Оба guard'а дают один
  и тот же внутренний `userId`.

### Связка аккаунтов
| Случай | Сложность |
|---|---|
| Аккаунт из Telegram задаёт себе логин и пароль | Простой |
| Аккаунт из браузера привязывает Telegram, у которого своих данных ещё нет | Простой |
| Слияние двух аккаунтов, в каждом из которых есть данные | Сложный — перешифровка всех данных; на первом этапе запретить |

### Миграции
Применяются сразу к проду (dev-базы нет): только forward, без изменения существующих id.
