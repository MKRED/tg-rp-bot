# План шага 3: UUID-пользователи и вход по логину

Шаг 3 роадмапа ([roadmap.md](roadmap.md)) разбит на четыре подшага, каждый деплоится отдельно:

| Подшаг | Что | Поведение для пользователя |
|---|---|---|
| **3a** | `users.id` → UUID, Telegram id — опциональное поле; перешифровка всех данных | не меняется |
| **3b** | вход по логину и паролю в браузере (второй guard) | новый способ входа |
| **3c** | логин и пароль для аккаунта из Telegram (настройки Mini App) | вход в браузере в тот же аккаунт |
| **3d** | привязка Telegram из браузера, отвязка, смена и восстановление пароля | привязка в настройках |

Почему так: 3a — самая рискованная часть (миграция прод-данных + шифрование), её выкатываем без новой
функциональности и смотрим логи. 3b–3d — обычная разработка поверх готовой схемы.

---

## Принятые решения

1. **Ключ шифрования** — случайный ключ на пользователя в `users.data_key` (вариант B ниже).
2. **Окно обслуживания** для 3a — согласовано.
3. **Репетиция** — на временной базе-копии на том же сервере (из резервной копии), затем прод.
   Резервная копия прода перед миграцией — `~/backups/tg-rp-bot/` на сервере.
4. **Сессии в браузере** — httpOnly-cookie (см. 3b).

## 3a — UUID и перешифровка ✅

**Готово 2026-10-11:** миграция `0043_users_uuid` и `scripts/migrate-user-keys` применены на проде
(12 пользователей, 5797 значений перешифровано, `v1` не осталось), код задеплоен. Резервная копия до
миграции — `~/backups/tg-rp-bot/kvach_telegram_rp_bot_20261011_005137_pre-0043.dump` на сервере.
Устройство шифрования — [architecture.md](../architecture.md#шифрование-данных-пользователя).

### Исходное состояние (прод, 2026-10-10)
- PostgreSQL 17, база ~26 МБ, 12 пользователей.
- `users.id bigint` = Telegram id; на него ссылаются 10 FK: `user_settings` (там `user_id` — PK),
  `characters`, `personas`, `cards`, `generation_presets`, `rp_templates`, `chats`, `knowledge_books`,
  `narrator_templates`, `story_chats`.
- Зашифровано ~3 тыс. строк (больше всего — `messages` 1121, `story_messages` 1604,
  `impersonation_variants` 205). Объём маленький → **одна транзакция**, без батчей.
- Ключ пользователя: `HKDF(masterKey, "tg-rp-bot-user-<telegramId>")` (`utils/crypto.ts`), токен
  `v1:` + base64(iv‖tag‖ciphertext).
- Миграции при старте контейнера **не применяются** (только вручную `drizzle-kit migrate`) — порядок
  переключения контролируем сами.

### Целевая схема
- `users.id uuid PRIMARY KEY DEFAULT gen_random_uuid()`.
- `users.telegram_id bigint UNIQUE NULL` — заполнен у привязавших Telegram (сейчас — у всех).
- Все `user_id` в 10 таблицах — `uuid` с теми же FK (`ON DELETE CASCADE`).
- dev-пользователь Claude: строка с `telegram_id = -1000000001`; dev-обход в guard остаётся «фальшивым
  Telegram id» и резолвится через `telegram_id`, как обычный пользователь Mini App.

### Ключ шифрования

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| A. Ключ из UUID | `HKDF(masterKey, "tg-rp-bot-user-<uuid>")` | минимум кода | ключ снова привязан к идентификатору; смена мастер-ключа = перешифровка всего |
| **B. Случайный ключ на пользователя (рекомендуется)** | 32 случайных байта, хранятся в `users.data_key`, зашифрованные мастер-ключом | ключ не зависит ни от каких id; смена мастер-ключа = перешифровать 1 поле на пользователя; удалить ключ = криптографически удалить данные | +1 колонка, +чтение ключа (кэш на процесс) |

Перешифровка всех данных нужна в обоих вариантах, поэтому B сейчас почти ничего не стоит, а потом
переход на него потребовал бы ещё одной такой же миграции.

Новый формат токена — **`v2:`** (тот же AES-256-GCM, другой ключ). Префикс делает скрипт идемпотентным и
даёт простую проверку: после миграции в базе не осталось ни одного `v1:`.

### Ловушка: `decryptField` и «legacy plaintext»
Сейчас любое значение без префикса `v1:` считается старым открытым текстом и отдаётся как есть. Если
старый код прочитает `v2:`-токен (или скрипт прервётся посередине), шифротекст уйдёт в UI как контент и
может быть сохранён обратно — тихая порча данных. Поэтому в 3a:
- `decryptField` **бросает** на любом `vN:`, кроме текущей версии;
- оставшиеся открытые legacy-значения шифруются тем же проходом скрипта, ветка «plaintext как есть»
  удаляется — в базе остаются только `v2:` и `null`.

### Инвентарь зашифрованных полей
Составляется по коду, а не по комментариям схемы: 16 репозиториев с `getUserEncryptionKey` +
`rp-chat/message-crypto.ts`. Обязательно учесть:
- jsonb `translations` у `messages` и `story_messages` — зашифровано **каждое значение**, ключи (коды
  языков) открыты;
- `user_settings`: ключи DeepSeek и Tavily;
- таблицы без `user_id` (`messages`, `story_messages`, `impersonation_variants`,
  `knowledge_book_entries`, `story_compactions`) — владелец (и ключ) определяется join'ом до родителя.

Страховка от пропущенного поля: проверочный запрос сканирует **все** text/jsonb-колонки всех таблиц на
`v1:` — должно быть 0.

### Миграция схемы (SQL вручную, одна транзакция)
`drizzle-kit generate` не умеет bigint→uuid с сохранением данных, поэтому SQL пишется руками
(`drizzle-kit generate --custom`), а `schema.ts` правится так, чтобы последующий `generate` был пустым.
1. `users`: добавить `new_id uuid DEFAULT gen_random_uuid()`, `telegram_id = id`, (B) `data_key text`.
2. В каждой из 10 таблиц: `user_uuid uuid`, заполнить join'ом `users.id → users.new_id`, `NOT NULL`.
3. Снять FK → снять PK `users` (и PK `user_settings`) → удалить старые колонки → переименовать
   `new_id → id`, `user_uuid → user_id` → вернуть PK, FK, индексы, `UNIQUE (telegram_id)`.

`telegram_id` сохраняет старый id, поэтому скрипт перешифровки может вывести старый ключ **после**
смены схемы.

### Скрипт перешифровки (`bot/scripts/`, TS, вне Nest)
- Для каждого пользователя: старый ключ из `telegram_id` (v1), новый — по выбранной схеме; (B) сгенерировать
  и сохранить `data_key`.
- Пройти инвентарь: `v1:` → расшифровать старым ключом → зашифровать новым (`v2:`); открытый текст →
  зашифровать; `v2:` — пропустить (идемпотентность).
- Всё в одной транзакции с миграцией схемы (или сразу после неё, той же транзакцией скрипта): при любой
  ошибке — откат, база в исходном виде.
- Лог: по таблицам — сколько перешифровано / пропущено / открытого текста зашифровано.
- Проверка в конце: 0 значений `v1:`; выборочно — расшифровка новым ключом совпадает с расшифровкой
  старым (хэши plaintext до/после по каждой строке на репетиции).

### Код (тот же коммит, что и миграция)
- `userId: number` → `string` (~95 файлов bot + `shared/src/debug.ts`). tsc поймает большую часть; руками
  проверить то, что он не ловит:
  - ключи блокировок в шаблонных строках, `Map`/`Set` по userId;
  - фильтр «только мои запросы» в `llm/debugCapture.ts`;
  - логи с `userId` (просто тип — без изменений смысла).
- `UsersService.ensureTelegramUser` → upsert `ON CONFLICT (telegram_id)`, возвращает uuid; кэш
  `telegramId → uuid` на процесс. Guard кладёт в запрос uuid.
- `/start`-обработчик бота — тот же upsert.
- `me/` уже работает с Telegram id из initData (`@TelegramUser()`) — без изменений.
- `utils/crypto.ts`: `getUserEncryptionKey(userId: string)` (A) или загрузка `data_key` (B), версия `v2:`,
  строгий `decryptField`. Тесты: шифрование/расшифровка, отказ на `v1:`/неизвестной версии.
- `docs/` и CLAUDE.md: убрать «users.id = Telegram id», описать новую схему ключей.

### Репетиция на локальной копии (до прода)
1. `pg_dump` прода → локальный Postgres 17 с pgvector (docker).
2. Прогнать миграцию + скрипт с прод-`ENCRYPTION_KEY`; проверки из скрипта + поштучная сверка хэшей.
3. Поднять бота на копии (`DATABASE_URL` на локальную базу), прокликать Mini App под dev-пользователем:
   персонажи, чаты, истории, книги, карточки, настройки ключей.
4. Удалить дамп и локальную базу.

Это первая «dev-база» проекта — заодно проверка, что так можно репетировать и будущие миграции.

### Переключение на проде (каждый шаг — с подтверждения владельца)
1. Зафиксировать текущий коммит `deploy` (откат).
2. Остановить контейнер (SSH).
3. `pg_dump` прода — резервная копия.
4. Миграция схемы + скрипт перешифровки (одна транзакция) → проверки.
5. Пуш `deploy` с новым кодом → контейнер стартует уже на новой схеме.
6. log-analyzer + проверка Mini App владельцем.

**Откат:** восстановить дамп + передеплоить коммит из п.1. Forward-исправление миграцией — только если
ошибка мелкая и данные целы.

## 3b — вход по логину и паролю ✅

**Выполнено и задеплоено (2026-10-11):** миграция `0044_user_sessions`; сервер (`auth/`) и webapp
(`features/auth/` — AuthGate над роутером вместо отдельных страниц `pages/auth/`). На проде проверены
регистрация, вход, выход, неверный пароль, CSRF и флаги cookie. Дальше — шаг 4 и 3c.

Цель: открыть приложение в обычном браузере (`https://miniapp.aoshi.ru`), зарегистрироваться или войти
по логину и паролю и работать с тем же API. Внутри Telegram всё остаётся как есть (initData).

### Принятые решения
1. **Сессия — httpOnly-cookie + таблица `user_sessions`**: случайный токен в cookie
   (`HttpOnly; Secure; SameSite=Lax`), в БД — его SHA-256 и срок. JS страницы токен не видит; выход =
   удаление строки.
2. **Логин и пароль — колонки в `users`**, отдельной таблицы нет. Пароль не шифруется, а хэшируется
   (scrypt): расшифровать его нельзя даже с мастер-ключом, только сверить.
3. **Регистрация открыта** всем.
4. **Срок сессии — 30 дней**, продлевается при использовании.
5. **Интерфейс «вход в браузере» в настройках Mini App — в 3c** (задать логин и пароль Telegram-аккаунту,
   привязка Telegram к браузерному). В 3b браузер и Telegram — отдельные способы входа; браузерный
   аккаунт создаётся регистрацией.

### Сервер
**Схема (миграция, обычная `generate`):**
- `users`: `login text UNIQUE NULL` (хранится в нижнем регистре), `password_hash text NULL` — заполнены
  у тех, кто задал вход по логину.
- `user_sessions`: `id uuid PK`, `user_id uuid FK users ON DELETE CASCADE`, `token_hash text UNIQUE`,
  `created_at`, `expires_at`, `last_used_at`, `user_agent text`.

**Пароли** — `scrypt` из `node:crypto` (без нативных зависимостей в образе), формат
`scrypt$N$r$p$salt$hash`, сравнение `timingSafeEqual`. Чистые функции + тесты. Правила: логин
`[a-z0-9_.-]{3,32}`, пароль 8–128 символов (верхняя граница — чтобы scrypt нельзя было загрузить
гигантским паролем). Лимиты — в `@tg-rp-bot/shared` (общие с формой).

**Модуль `auth/`** (расширение):
- `POST /api/auth/register` `{ login, password }` → строка `users` (без `telegram_id`, с новым
  `data_key`, логином и хэшем пароля) + сессия; `201 { ok: true }`, `409 login_taken`.
- `POST /api/auth/login` → сессия; на любую ошибку один ответ `401 invalid_credentials` (не
  подсказываем, существует ли логин).
- `POST /api/auth/logout` → удаляет сессию, гасит cookie.
- `GET /api/auth/session` → `{ id, login | null, telegramLinked, displayName }` — профиль для webapp в
  браузере (initData там нет); 401 без сессии.
- register/login — `@Public()` + ограничение частоты (`@nestjs/throttler`, по IP; за nginx —
  `trust proxy`, чтобы IP брался из `X-Forwarded-For`).

**Guard:** `TelegramAuthGuard` → общий `AuthGuard` с порядком: заголовок `tma …` → initData (как
сейчас); иначе cookie сессии → `user_id` из `user_sessions` (с продлением срока); иначе dev-обход
(только локально); иначе 401. Оба пути кладут в запрос один и тот же внутренний `userId` —
контроллеры не меняются. `request.tgUser` становится необязательным: `me/` (профиль Telegram, Bot API)
без Telegram отвечает `409 telegram_not_linked`.

**CSRF:** `SameSite=Lax` не отправляет cookie с чужих сайтов на POST/PUT/DELETE; плюс для запросов по
cookie сервер требует собственный заголовок (`X-Requested-With`), который чужая страница без CORS не
может поставить. CORS не включаем.

**Просроченные сессии** удаляются при попытке входа с ними и периодической чисткой при старте.

### Webapp
- Режим определяется один раз при старте: есть `initData.raw()` → Telegram (как сейчас), иначе браузер.
- Браузер: `GET /api/auth/session` → есть сессия — приложение; нет — экран входа со ссылкой на
  регистрацию (и наоборот).
- `apiFetch`/SSE-ридеры: в браузере без `Authorization`, cookie уходит сам (same-origin), плюс
  `X-Requested-With`. Ответ 401 в браузере → экран входа.
- Новая фича `features/auth/` + страницы `pages/auth/`: вход, регистрация (формы на Mantine).
- Главная: имя в браузере — из сессии (вместо `initData.user()`); фото профиля Telegram — только при
  привязанном Telegram.
- В браузере — кнопка «Выйти» (настройки).
- Telegram-only функции (BackButton, отправка фото в чат, полноэкранный режим) в браузере уже
  выключаются защитами SDK; кнопку «отправить в чат» скрыть без привязанного Telegram.

### Порядок работ
1. Схема + пароли + сессии + `AuthGuard` + `auth/` на сервере, тесты (сервисы с мок-
   репозиториями, DTO, guard). Telegram-путь не меняется — можно деплоить отдельно.
2. Webapp: режим браузера, вход/регистрация, профиль, настройки. Проверка Playwright'ом локально.
3. Деплой, проверка на проде: регистрация и вход из браузера.
4. Шаг 4 роадмапа: Claude регистрирует себе браузерный аккаунт на проде (пароль — в локальном
   `bot/.env`, в чат не попадает) и проверяет задеплоенное приложение через Playwright.

### Вне 3b
- Восстановление пароля — только через привязанный Telegram (3d); без Telegram восстановления нет —
  предупреждаем при регистрации.
- Задать логин и пароль Telegram-аккаунту — 3c; привязка/отвязка Telegram — 3d.

## 3c — логин и пароль из Mini App

**Сделано локально, не задеплоено.** Основной путь связки аккаунтов: все существующие пользователи
пришли из Telegram, и их данные там. Аккаунт задаёт себе логин и пароль в настройках Mini App и
дальше входит с ними в браузере в тот же аккаунт.

- **Сервер:** `PUT /api/auth/credentials` `{ login, password }` → `200 { ok: true }`.
  - Пускает только вход по initData: `@TelegramUser()`, по cookie ответ `409 telegram_not_linked`.
    Старый пароль не спрашиваем, личность подтверждает initData.
  - Логин задаётся один раз: `UPDATE … WHERE login IS NULL` одним запросом. Если логин занят —
    `409 login_taken`, если уже задан — `409 login_already_set`.
  - Действует тот же лимит частоты, что у входа.
- **Webapp:** секция «Вход в браузере» в настройках (`features/auth/`: `useBrowserLogin`,
  `BrowserLoginSection`).
  - Без логина — форма «логин + пароль + повтор» с теми же проверками, что при регистрации.
  - С логином — показываем логин и адрес для входа.
  - Секция видна в Mini App и при пустом логине, то есть и в локальном dev-обходе, чтобы её можно
    было проверить вне Telegram.
- **Проверено локально** dev-пользователем:
  - несовпадение паролей и занятый логин;
  - сохранение;
  - повторное задание (`login_already_set`) и запрос по cookie (`telegram_not_linked`);
  - вход с новым логином попадает в тот же аккаунт.

  После проверки тестовый логин сброшен.
- **На проде** форму проверяет владелец (Mini App нужен initData).

## 3d — привязка Telegram из браузера, отвязка, смена и восстановление пароля

Браузерный аккаунт привязывает Telegram через бота. Аккаунт с логином может отвязать Telegram,
сменить пароль или восстановить его через Telegram.

### Принятые решения
1. **Логин и пароль Telegram-аккаунту** задаются в Mini App (сделано в 3c).
2. **Восстановление пароля = смена пароля из Mini App.** initData уже доказывает, что это владелец
   Telegram, поэтому токены сброса и письма не нужны. Без привязанного Telegram восстановления нет
   (так и было в 3b).
3. **Привязка Telegram к браузерному аккаунту** работает через deep link
   `t.me/<бот>?start=link_<токен>`:
   - токен одноразовый, живёт 15 минут, в БД хранится только его SHA-256;
   - пользователь открывает ссылку и жмёт Start, бот записывает его `telegram_id` в браузерный аккаунт.
4. **Слияние двух аккаунтов с данными запрещено.** Для этого пришлось бы перешифровывать данные одного
   аккаунта ключом другого. Пустой аккаунт можно удалить.
5. **Отвязка Telegram** разрешена только при заданных логине и пароле и требует ввести текущий пароль:
   это заодно проверка, что пользователь сможет войти после отвязки.

### Исходы привязки (deep link)

Обозначения: **Б** — браузерный аккаунт, у которого запросили ссылку; **Т** — аккаунт, у которого
уже есть этот `telegram_id`.

| Ситуация | Исход |
|---|---|
| Т нет | `telegram_id` и имя из Telegram записываются в Б |
| Т есть и пустой | Т удаляется, Telegram привязывается к Б (одна транзакция) |
| Т с данными, Б пустой | ❓ **вопрос владельцу**: (а) перенести логин и хэш пароля Б в Т, а Б удалить (его сессии удалятся каскадом, следующий вход тем же паролем попадёт в Т), или (б) отказать с подсказкой «войдите в Mini App и задайте логин там» |
| Т и Б с данными | отказ: «у этого Telegram уже есть аккаунт с данными, слияние пока невозможно» |
| У Б уже есть Telegram | ссылку не выдаём (409 `telegram_already_linked`) |
| Токен просрочен или использован | бот отвечает, что ссылка устарела, и просит получить новую в настройках |

**«Пустой аккаунт»** — ни одной строки во всех таблицах с FK на `users`, кроме:
- `user_sessions` — сессии не считаются данными;
- `user_settings` — считается пустой, если в ней не сохранены ключи DeepSeek/Tavily (❓ **вопрос
  владельцу**: сохранённые ключи — это данные, и удалять их молча нельзя; предлагаю считать аккаунт
  с ключом непустым).

Сейчас FK на `users` есть у 11 таблиц из 19. Список проверяемых таблиц держим в одном месте, а
юнит-тест обходит drizzle-схему и сверяет её FK на `users` с этим списком. Так новая таблица с
данными пользователя не превратит «пустой» аккаунт в аккаунт с данными, которые удалятся молча.

### Сервер

**Схема (миграция через обычный `generate`):** `telegram_link_tokens`:
- `token_hash text PK`;
- `user_id uuid FK users ON DELETE CASCADE`;
- `expires_at`, `created_at`.

У пользователя одна активная ссылка: при выдаче новой старые его токены удаляются. Просроченные
токены вычищаются при старте, как сессии.

**API (`auth/`, всё под `ThrottlerGuard`, CSRF уже проверяет guard):**

| Маршрут | Кто | Что делает |
|---|---|---|
| `PUT /api/auth/password` `{ currentPassword?, password }` | initData или cookie | смена пароля; через initData `currentPassword` не нужен (восстановление), через cookie обязателен (`401 invalid_credentials`). Отзывает все сессии, кроме текущей (cookie) или все (initData) |
| `POST /api/auth/telegram-link` | cookie, Telegram не привязан | выдаёт `{ url }` со свежим токеном |
| `DELETE /api/auth/telegram` `{ password }` | initData или cookie, логин задан | отвязать Telegram: `telegram_id`, `username` и имя Telegram → NULL |

`GET /api/auth/session` уже отдаёт `login` и `telegramLinked`, его хватает для экранов. Для
восстановления пароля добавить только поле `hasPassword`.

**Бот: `/start link_<токен>`** (`StartHandler`, payload берётся из `ctx.match`):
- ⚠️ при `link_`-payload `saveTelegramProfile` **не вызывается**. Иначе upsert заведёт пустой
  Т-аккаунт раньше привязки, и каждая привязка будет уходить в ветку «Т есть»;
- погашение токена (`DELETE … RETURNING`), проверка Т, удаление пустого Т и запись `telegram_id` в Б
  идут **одной транзакцией** в `users.repository`. Гонку двух привязок закрывает UNIQUE на
  `telegram_id`, она даёт отказ, а не двойную запись;
- ответ: «Telegram привязан к аккаунту `<логин>`» плюс кнопка Mini App, или текст отказа из таблицы
  исходов;
- только личный чат (`/start` с payload из группы игнорируется).

**Чистая логика с тестами:**
- `parseLinkPayload` — формат `link_` + base64url;
- `decideLinkOutcome` — по состоянию Б и Т возвращает исход из таблицы;
- сервис привязки — с мок-репозиторием;
- DTO.

Токен: 24 случайных байта в base64url (32 символа). С префиксом это 37 символов, укладывается в
лимит payload Telegram (64 символа `[A-Za-z0-9_-]`).

**Имя бота для ссылки:** локально polling выключен, и `botInfo` там пуст. Берём `bot.api.getMe()`
один раз, лениво, с кэшем: запрос идёт через прокси и работает и локально. Отдельный env не нужен.

**⚠️ Инвариант — кэш `UsersService.ensured`** (Telegram id → userId, живёт весь процесс). Привязка,
отвязка и удаление пустого Т обязаны удалять из него запись. Иначе Mini App до рестарта будет
ходить под удалённым или старым userId. Бот и API живут в одном процессе, так что достаточно
метода `UsersService.forgetTelegram(telegramId)`.

**Отвязка из Mini App:** следующий запрос с initData заведёт этому Telegram новый пустой аккаунт.
Webapp предупреждает об этом до отвязки, а после неё показывает экран «Telegram отвязан, войдите в
браузере».

### Webapp
Новая секция «Вход в браузере» в настройках (`features/auth/`, формы на Mantine):
- **в Mini App, логин не задан:** форма «логин + пароль + повтор» и пояснение, зачем это нужно:
  вход с компьютера и в браузере;
- **в Mini App, логин задан:** логин (только чтение), «Сменить пароль» без старого пароля (с
  подсказкой, что так же восстанавливается забытый пароль), «Отвязать Telegram» с подтверждением
  паролем и предупреждением;
- **в браузере, Telegram не привязан:** кнопка «Привязать Telegram» открывает `url` (это
  `t.me`-ссылка, в браузере она откроет Telegram). Пока экран открыт, сессия перезапрашивается при
  возврате на вкладку (`visibilitychange`) и раз в несколько секунд, в течение 15 минут, пока
  `telegramLinked` не станет `true`;
- **в браузере, Telegram привязан:** «Сменить пароль» со старым паролем и «Отвязать Telegram».

На экране входа в браузере — подсказка «Забыли пароль? Откройте приложение в Telegram → Настройки →
Вход в браузере».

### Порядок работ
1. **Сервер:**
   - миграция `telegram_link_tokens`;
   - `password`, `telegram-link`, отвязка;
   - проверка пустоты аккаунта и тест сверки FK со схемой;
   - `decideLinkOutcome` и `parseLinkPayload`;
   - `/start link_…`, удаление из `ensured`;
   - тесты сервисов, DTO и чистых функций.
2. **Webapp:**
   - секция настроек в обоих режимах;
   - подсказка на экране входа;
   - локальная проверка Playwright: сменить пароль, выдать ссылку, отвязать. Тестовые логины
     удаляются после проверки.
3. **Деплой.**
   - Claude проверяет на проде то, что делается из браузера, своим аккаунтом `claude`: смену пароля
     и выдачу ссылки (без нажатия Start).
   - Привязку по deep link проверяет **владелец** на проде: локально `BOT_POLLING` запрещён, а
     Claude не может нажать Start в Telegram. Сценарий для владельца:
     1. зарегистрировать в браузере тестовый аккаунт;
     2. нажать «Привязать Telegram» → Start;
     3. ⚠️ основной Telegram владельца уже связан с аккаунтом с данными, поэтому тест покажет ветку
        отказа. Ветку «Т нет» проверить можно только вторым Telegram-аккаунтом.
   - Затем логи и удаление тестовых аккаунтов.
