# План шага 3: UUID-пользователи и вход по логину

Шаг 3 роадмапа ([roadmap.md](roadmap.md)) разбит на три подшага, каждый деплоится отдельно:

| Подшаг | Что | Поведение для пользователя |
|---|---|---|
| **3a** | `users.id` → UUID, Telegram id — опциональное поле; перешифровка всех данных | не меняется |
| **3b** | вход по логину и паролю в браузере (второй guard) | новый способ входа |
| **3c** | связка аккаунтов (Telegram ↔ логин) | привязка в настройках |

Почему так: 3a — самая рискованная часть (миграция прод-данных + шифрование), её выкатываем без новой
функциональности и смотрим логи. 3b/3c — обычная разработка поверх готовой схемы.

---

## Принятые решения

1. **Ключ шифрования** — случайный ключ на пользователя в `users.data_key` (вариант B ниже).
2. **Окно обслуживания** для 3a — согласовано.
3. **Репетиция** — на временной базе-копии на том же сервере (из резервной копии), затем прод.
   Резервная копия прода перед миграцией — `~/backups/tg-rp-bot/` на сервере.
4. **Сессии в браузере** — решаем в начале 3b (см. ниже).

## 3a — UUID и перешифровка ✅

**Готово 2026-10-11:** миграция `0043_users_uuid` и `scripts/migrate-user-keys` применены на проде
(12 пользователей, 5797 значений перешифровано, `v1` не осталось), код задеплоен. Резервная копия до
миграции — `~/backups/tg-rp-bot/kvach_telegram_rp_bot_20261011_005137_pre-0043.dump` на сервере.
Устройство шифрования — [architecture.md](../architecture.md#шифрование-данных-пользователя).

### Исходное состояние (прод, 2026-10-10)
- PostgreSQL 17, база ~26 МБ, 12 пользователей.
- `users.id bigint` = Telegram id; на него ссылаются 10 FK: `user_settings` (там `user_id` — PK),
  `characters`, `personas`, `cards`, `generation_presets`, `rp_templates`, `chats`, `knowledge_books`,
  `narrator_templates`, `story_chats`.
- Зашифровано ~3 тыс. строк (больше всего — `messages` 1121, `story_messages` 1604,
  `impersonation_variants` 205). Объём маленький → **одна транзакция**, без батчей.
- Ключ пользователя: `HKDF(masterKey, "tg-rp-bot-user-<telegramId>")` (`utils/crypto.ts`), токен
  `v1:` + base64(iv‖tag‖ciphertext).
- Миграции при старте контейнера **не применяются** (только вручную `drizzle-kit migrate`) — порядок
  переключения контролируем сами.

### Целевая схема
- `users.id uuid PRIMARY KEY DEFAULT gen_random_uuid()`.
- `users.telegram_id bigint UNIQUE NULL` — заполнен у привязавших Telegram (сейчас — у всех).
- Все `user_id` в 10 таблицах — `uuid` с теми же FK (`ON DELETE CASCADE`).
- dev-пользователь Claude: строка с `telegram_id = -1000000001`; dev-обход в guard остаётся «фальшивым
  Telegram id» и резолвится через `telegram_id`, как обычный пользователь Mini App.

### Ключ шифрования

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| A. Ключ из UUID | `HKDF(masterKey, "tg-rp-bot-user-<uuid>")` | минимум кода | ключ снова привязан к идентификатору; смена мастер-ключа = перешифровка всего |
| **B. Случайный ключ на пользователя (рекомендуется)** | 32 случайных байта, хранятся в `users.data_key`, зашифрованные мастер-ключом | ключ не зависит ни от каких id; смена мастер-ключа = перешифровать 1 поле на пользователя; удалить ключ = криптографически удалить данные | +1 колонка, +чтение ключа (кэш на процесс) |

Перешифровка всех данных нужна в обоих вариантах, поэтому B сейчас почти ничего не стоит, а потом
переход на него потребовал бы ещё одной такой же миграции.

Новый формат токена — **`v2:`** (тот же AES-256-GCM, другой ключ). Префикс делает скрипт идемпотентным и
даёт простую проверку: после миграции в базе не осталось ни одного `v1:`.

### Ловушка: `decryptField` и «legacy plaintext»
Сейчас любое значение без префикса `v1:` считается старым открытым текстом и отдаётся как есть. Если
старый код прочитает `v2:`-токен (или скрипт прервётся посередине), шифротекст уйдёт в UI как контент и
может быть сохранён обратно — тихая порча данных. Поэтому в 3a:
- `decryptField` **бросает** на любом `vN:`, кроме текущей версии;
- оставшиеся открытые legacy-значения шифруются тем же проходом скрипта, ветка «plaintext как есть»
  удаляется — в базе остаются только `v2:` и `null`.

### Инвентарь зашифрованных полей
Составляется по коду, а не по комментариям схемы: 16 репозиториев с `getUserEncryptionKey` +
`rp-chat/message-crypto.ts`. Обязательно учесть:
- jsonb `translations` у `messages` и `story_messages` — зашифровано **каждое значение**, ключи (коды
  языков) открыты;
- `user_settings`: ключи DeepSeek и Tavily;
- таблицы без `user_id` (`messages`, `story_messages`, `impersonation_variants`,
  `knowledge_book_entries`, `story_compactions`) — владелец (и ключ) определяется join'ом до родителя.

Страховка от пропущенного поля: проверочный запрос сканирует **все** text/jsonb-колонки всех таблиц на
`v1:` — должно быть 0.

### Миграция схемы (SQL вручную, одна транзакция)
`drizzle-kit generate` не умеет bigint→uuid с сохранением данных, поэтому SQL пишется руками
(`drizzle-kit generate --custom`), а `schema.ts` правится так, чтобы последующий `generate` был пустым.
1. `users`: добавить `new_id uuid DEFAULT gen_random_uuid()`, `telegram_id = id`, (B) `data_key text`.
2. В каждой из 10 таблиц: `user_uuid uuid`, заполнить join'ом `users.id → users.new_id`, `NOT NULL`.
3. Снять FK → снять PK `users` (и PK `user_settings`) → удалить старые колонки → переименовать
   `new_id → id`, `user_uuid → user_id` → вернуть PK, FK, индексы, `UNIQUE (telegram_id)`.

`telegram_id` сохраняет старый id, поэтому скрипт перешифровки может вывести старый ключ **после**
смены схемы.

### Скрипт перешифровки (`bot/scripts/`, TS, вне Nest)
- Для каждого пользователя: старый ключ из `telegram_id` (v1), новый — по выбранной схеме; (B) сгенерировать
  и сохранить `data_key`.
- Пройти инвентарь: `v1:` → расшифровать старым ключом → зашифровать новым (`v2:`); открытый текст →
  зашифровать; `v2:` — пропустить (идемпотентность).
- Всё в одной транзакции с миграцией схемы (или сразу после неё, той же транзакцией скрипта): при любой
  ошибке — откат, база в исходном виде.
- Лог: по таблицам — сколько перешифровано / пропущено / открытого текста зашифровано.
- Проверка в конце: 0 значений `v1:`; выборочно — расшифровка новым ключом совпадает с расшифровкой
  старым (хэши plaintext до/после по каждой строке на репетиции).

### Код (тот же коммит, что и миграция)
- `userId: number` → `string` (~95 файлов bot + `shared/src/debug.ts`). tsc поймает большую часть; руками
  проверить то, что он не ловит:
  - ключи блокировок в шаблонных строках, `Map`/`Set` по userId;
  - фильтр «только мои запросы» в `llm/debugCapture.ts`;
  - логи с `userId` (просто тип — без изменений смысла).
- `UsersService.ensureTelegramUser` → upsert `ON CONFLICT (telegram_id)`, возвращает uuid; кэш
  `telegramId → uuid` на процесс. Guard кладёт в запрос uuid.
- `/start`-обработчик бота — тот же upsert.
- `me/` уже работает с Telegram id из initData (`@TelegramUser()`) — без изменений.
- `utils/crypto.ts`: `getUserEncryptionKey(userId: string)` (A) или загрузка `data_key` (B), версия `v2:`,
  строгий `decryptField`. Тесты: шифрование/расшифровка, отказ на `v1:`/неизвестной версии.
- `docs/` и CLAUDE.md: убрать «users.id = Telegram id», описать новую схему ключей.

### Репетиция на локальной копии (до прода)
1. `pg_dump` прода → локальный Postgres 17 с pgvector (docker).
2. Прогнать миграцию + скрипт с прод-`ENCRYPTION_KEY`; проверки из скрипта + поштучная сверка хэшей.
3. Поднять бота на копии (`DATABASE_URL` на локальную базу), прокликать Mini App под dev-пользователем:
   персонажи, чаты, истории, книги, карточки, настройки ключей.
4. Удалить дамп и локальную базу.

Это первая «dev-база» проекта — заодно проверка, что так можно репетировать и будущие миграции.

### Переключение на проде (каждый шаг — с подтверждения владельца)
1. Зафиксировать текущий коммит `deploy` (откат).
2. Остановить контейнер (SSH).
3. `pg_dump` прода — резервная копия.
4. Миграция схемы + скрипт перешифровки (одна транзакция) → проверки.
5. Пуш `deploy` с новым кодом → контейнер стартует уже на новой схеме.
6. log-analyzer + проверка Mini App владельцем.

**Откат:** восстановить дамп + передеплоить коммит из п.1. Forward-исправление миграцией — только если
ошибка мелкая и данные целы.

## 3b — вход по логину и паролю

Цель: открыть приложение в обычном браузере (`https://miniapp.aoshi.ru`), зарегистрироваться или войти
по логину и паролю и работать с тем же API. Внутри Telegram всё остаётся как есть (initData).

### Решения, нужные до начала
1. **Где хранить сессию в браузере** (рекомендуется A):

   | Вариант | Как | Плюсы | Минусы |
   |---|---|---|---|
   | **A. httpOnly-cookie + таблица сессий** | случайный токен в cookie (`HttpOnly; Secure; SameSite=Lax`), в БД — его SHA-256 и срок | JS страницы не видит токен (XSS его не украдёт); выход и «выйти на всех устройствах» = удаление строк | нужна защита от CSRF (см. ниже), +1 таблица |
   | B. Токен в localStorage, заголовок `Authorization: Bearer` | тот же токен и таблица, но хранит webapp | ложится на текущий `apiFetch`; CSRF не нужен | любой XSS уносит сессию |
   | C. JWT без таблицы | подписанный токен | без запросов к БД | не отозвать до истечения — не подходит |

2. **Регистрация в браузере** (рекомендуется открытая): любой может завести аккаунт по логину и
   паролю (ключи LLM у каждого свои — BYOK, стоимость генерации на нас не ложится). Альтернатива —
   закрытая: логин и пароль задаёт себе только аккаунт, уже созданный через Telegram.
3. **Срок сессии** — по умолчанию 30 дней, продлевается при использовании.

### Сервер
**Схема (миграция, обычная `generate`):**
- `user_credentials`: `user_id uuid PK FK users ON DELETE CASCADE`, `login text` (хранится в нижнем
  регистре, `UNIQUE`), `password_hash text`, `created_at`, `updated_at`.
- `user_sessions` (вариант A/B): `id uuid PK`, `user_id uuid FK CASCADE`, `token_hash text UNIQUE`,
  `created_at`, `expires_at`, `last_used_at`, `user_agent text`.

**Пароли** — `scrypt` из `node:crypto` (без нативных зависимостей в образе), формат
`scrypt$N$r$p$salt$hash`, сравнение `timingSafeEqual`. Чистые функции + тесты. Правила: логин
`[a-z0-9_.-]{3,32}`, пароль 8–128 символов (верхняя граница — чтобы scrypt нельзя было загрузить
гигантским паролем). Лимиты — в `@tg-rp-bot/shared` (общие с формой).

**Модуль `auth/`** (расширение):
- `POST /api/auth/register` `{ login, password }` → создаёт `users` (без `telegram_id`, с новым
  `data_key`) + `user_credentials` + сессию; `201 { ok: true }`, `409 login_taken`.
- `POST /api/auth/login` → сессия; на любую ошибку один ответ `401 invalid_credentials` (не
  подсказываем, существует ли логин).
- `POST /api/auth/logout` → удаляет сессию, гасит cookie.
- register/login — `@Public()` + ограничение частоты (`@nestjs/throttler`, по IP; за nginx —
  `trust proxy`, чтобы IP брался из `X-Forwarded-For`).

**Guard:** `TelegramAuthGuard` → общий `AuthGuard` с порядком: заголовок `tma …` → initData (как
сейчас); иначе cookie сессии → `user_id` из `user_sessions`; иначе dev-обход (только локально); иначе
401. Оба пути кладут в запрос один и тот же внутренний `userId` — контроллеры не меняются.
`request.tgUser` становится необязательным: `me/` (профиль Telegram, Bot API) без Telegram отвечает
`409 telegram_not_linked`.

**CSRF (вариант A):** `SameSite=Lax` не отправляет cookie с чужих сайтов на POST/PUT/DELETE; плюс
для запросов по cookie сервер требует собственный заголовок (`X-Requested-With`), который чужая страница
без CORS не может поставить. CORS не включаем.

**Модуль `account/`** (новый префикс `/api/account`):
- `GET /api/account` → `{ id, login | null, telegramLinked, displayName }` — профиль для webapp в
  браузере (initData там нет).
- `PUT /api/account/credentials` `{ login, password, currentPassword? }` — задать или сменить логин и
  пароль; при смене обязателен текущий пароль. Так владелец из Telegram заводит себе вход для браузера.
- При смене пароля — удалить остальные сессии пользователя.

### Webapp
- Режим определяется один раз при старте: есть `initData.raw()` → Telegram (как сейчас), иначе браузер.
- `apiFetch`/SSE-ридеры: в браузере без `Authorization`, cookie уходит сам (same-origin), плюс
  `X-Requested-With`. Ответ 401 в браузере → экран входа.
- Новая фича `features/auth/` + страницы `pages/auth/`: вход, регистрация (tgui-формы).
- Главная: имя и аватар в браузере — из `GET /api/account` (вместо `initData.user()`); фото профиля
  Telegram — только при привязанном Telegram.
- Настройки: секция «Вход в браузере» — задать или сменить логин и пароль (видна и в Telegram);
  в браузере — «Выйти».
- Telegram-only функции (BackButton, отправка фото в чат, полноэкранный режим) в браузере уже
  выключаются защитами SDK; кнопку «отправить в чат» скрыть без привязанного Telegram.

### Порядок работ
1. Схема + пароли + сессии + `AuthGuard` + `auth/` и `account/` на сервере, тесты (сервисы с мок-
   репозиториями, DTO, guard). Telegram-путь не меняется — можно деплоить отдельно.
2. Webapp: режим браузера, вход/регистрация, профиль, настройки. Проверка Playwright'ом локально.
3. Деплой, проверка на проде: вход владельца из браузера после задания пароля в Mini App.
4. Шаг 4 роадмапа: логин для Claude (dev-пользователь получает логин; пароль задаёт владелец, в чат он
   не попадает) — Claude проверяет задеплоенное приложение через Playwright.

### Вне 3b
- Восстановление пароля — только через привязанный Telegram (3c); без Telegram восстановления нет —
  предупреждаем при регистрации.
- Привязка/отвязка Telegram — 3c.

## 3c — связка аккаунтов (эскиз)

| Случай | Решение |
|---|---|
| Аккаунт из Telegram задаёт логин и пароль | в настройках Mini App, просто создаёт `user_credentials` |
| Браузерный аккаунт привязывает Telegram | deep link `t.me/<бот>?start=link_<одноразовый токен>` → бот записывает `telegram_id` |
| У этого Telegram уже есть аккаунт без данных | пустой аккаунт удаляется, Telegram привязывается |
| У обоих аккаунтов есть данные | на первом этапе запрещено (слияние = перешифровка данных одного из них) |
| Отвязка Telegram | только если задан логин и пароль (иначе аккаунт станет недоступен) |
