# Соавтор

Чат с ИИ над несколькими карточками сразу (до `MAX_COAUTHOR_CARDS = 4`). Модель сама читает нужные
карточки чата (текст и картинки-референсы) и предлагает правки блоков. Пользователь принимает или отклоняет каждую правку, без его решения
карточки не меняются. Главный случай — связанные персонажи: например, вторую сестру дописывают, когда
первая уже готова.

- Код: `bot/src/coauthor/` (API `/api/coauthor`), `webapp/src/features/coauthor/`,
  `webapp/src/pages/coauthor/`.
- Контракт: `shared/src/coauthor.ts`.
- Таблица: `coauthor_chats`.

## Хранение

Одна строка на чат:
- `card_ids` — карточки по порядку. Это не FK: удалённая карточка просто пропадает из чата на чтении.
- `preset_id`, `use_web_search`, `use_images`.
- `max_rounds`, `max_edits`, `max_questions` — лимиты хода (`COAUTHOR_LIMITS` в `shared/src/coauthor.ts`).
- `system_prompt` — своя часть промпта.
- `state` — вся переписка с моделью, правки, ожидающие вопросы и решения пользователя
  (`CoauthorState`, `bot/src/coauthor/turn/state.ts`). Хранится одним JSON, зашифрованным per-user ключом.

Лента для экрана (`feed`) не хранится: её собирает `turn/feed.ts` из истории протокола.

## Промпт (`turn/prompt.ts` — тексты, `turn/input.ts` — сборка запроса)

Соавтор ходит в **Responses API** DeepSeek (`LlmService.respond`, [llm.md](llm.md#responses-api-соавтор)),
поэтому запрос — массив элементов `input`, а не `messages`:

```
system:               своя часть пользователя (или DEFAULT_COAUTHOR_SYSTEM_PROMPT) + неизменяемый протокол
…история (обрезана trimHistory, начинается с user), в каждом ходе:
user:                 сообщение пользователя ([Review: …] + текст)
reasoning + function_call: list_cards        ← синтетический, пишется в историю в начале хода
function_call_output: card_id, name, reference_images, read?, blocks[block_id, title, written]
…вызовы модели: get_card → текст карточки + картинки, edit_block / apply_patch, ask_user, web_search
assistant:            ответ
```

- **История хранится в прежнем chat-формате** (`StoredMessage`: `toolCalls`, `role: "tool"`) — так записаны
  все существующие чаты. В элементы Responses её переводит `turn/input.ts` при каждой сборке запроса:
  вызов → `[reasoning] → [assistant-текст] → function_call…`, результат → `function_call_output`.
  Состояние не мигрируется.
- **Карточек в промпте нет — модель читает их сама** (`turn/card-context/`):
  - В начале хода после сообщения пользователя в историю пишется синтетический вызов `list_cards` с
    результатом (`opening.ts`): что открыто, какие блоки написаны и `read: true` у карточек, актуальный
    `get_card` которых уже есть в разговоре (без этой подсказки модель перечитывала карточки каждый ход).
    Вызов именно хранится, а не подставляется при сборке: иначе история прошлых ходов менялась бы задним
    числом и кэш провайдера сбрасывался бы каждый ход. В ленте его нет (`isAutoListCall`).
  - `get_card(card_id)` возвращает JSON карточки (`render.ts`: `version`, `brief`, блоки с `path`, `format`,
    `content`, `pending_proposal`). В историю пишется только текст; картинки-референсы прикладывает сборка
    запроса из текущей карточки — в БД data URL не попадают.
  - **Версия карточки** (`cardVersion`) — хэш её текста, картинок и решений пользователя по правкам.
    Свои ожидающие правки модели в неё **не** входят: модель о них знает, иначе каждая правка делала бы
    карточку устаревшей посреди хода.
  - **Заглушки** (`replay.ts`): результат прошлых ходов заменяется короткой заметкой, если версия карточки
    сменилась («Outdated… call get_card again»), карточку убрали из чата или есть более поздний результат той же
    карточки. Результаты **текущего** хода не трогаются никогда — внутри хода запрос каждого раунда побайтно
    продолжает предыдущий (кэш; иначе картинки оплачивались бы на каждом раунде). Старый `get_cards` из
    прежних чатов — всегда заглушка про удалённый инструмент.
  - **Править можно только прочитанную карточку**: `edit_block` / `apply_patch` по карточке без актуального
    результата `get_card` в видимой (обрезанной) истории — ошибка «call get_card(N) first». Прочитанное в том
    же раунде не в счёт: результат модель увидит только в следующем.
- **Картинки-референсы** (тумблер чата `use_images`) уходят в результате `get_card` с подписью
  «Reference images of <name> (card_id N)» — модель их видит (проверено пробой). Шлются, только если модель
  пресета видит картинки (`modelSupportsImages`). Модель без зрения не падает, а молча выкидывает их, поэтому
  чат работает и без них, а webapp гасит тумблер с подсказкой. Картинка ≈ 1000 токенов. В следующих раундах
  хода она в кэшированном префиксе. С новым сообщением пользователя из прошлого хода уходят рассуждения,
  поэтому картинки, прочитанные в непосредственно предыдущем ходе, один раз оплачиваются без кэша; дальше они снова в кэше,
  пока карточка не изменилась.
- **Своя часть промпта — только правила поведения** (тон, язык, что менять). Протокол инструментов
  дописывает сервер, поэтому правка промпта пользователем не ломает механику правок.
  - Стандартный промпт: с пользователем — на языке его последнего сообщения, блоки — всегда на английском
    (их читает другая модель при игре). Блок не на английском при правке переписывается целиком через
    `edit_block`, а не патчится, — иначе получится смесь языков.
  - Пустая строка в чате — стандартный промпт. Так улучшения стандарта доходят до чатов, где промпт не меняли.
  - В webapp редактор показывает стандартный текст. Если правка совпала со стандартом, сохраняется `""`.
- **Решения пользователя** копятся в `reviewNotes` и уходят модели префиксом `[Review: …]` к следующему
  сообщению пользователя. На экране этот префикс не показывается.
- **Обрезка истории** (`turn/trim.ts`) — по бюджету `COAUTHOR_HISTORY_TOKEN_BUDGET`.
  - Режем только целыми ходами («сообщение пользователя → всё до следующего»), поэтому вызовы инструментов
    не отрываются от своих результатов, а история всегда начинается с `user`.
  - Последний ход остаётся целиком.
  - Результат `get_card`, который уйдёт заглушкой, весит при обрезке как заглушка, а не как хранимый текст
    карточки (`card-context/visible.ts`). Это же окно используется для проверки «карточка прочитана» и для
    `read` в `list_cards`.

## Ход (`turn/turn-loop.ts`, `coauthor-turn.service.ts`)

**Инструменты** (везде `tool_choice: "auto"` — принудительный выбор DeepSeek в thinking-режиме отклоняет):
- `list_cards`, `get_card(card_id)` — чтение карточек (см. выше);
- `apply_patch` — **custom-инструмент** Responses API (DeepSeek принимает только это имя, формат патча Codex):
  точечные правки, несколько блоков и карточек за вызов (`turn/patch-proposals.ts`, разбор — `turn/apply-patch/`);
- `edit_block(card_id, block_id, content)` — полная замена блока: заполнить пустой или переписать целиком
  (`turn/proposals.ts`);
- `ask_user` — пауза до ответа пользователя. Включён **всегда**: уточнения — часть совместной работы, частоту
  задаёт лимит `maxQuestions`, а не тумблер;
- `web_search` — если включён в чате.

**Правки** (`turn/proposals.ts`):
- Невалидные id, пустой текст и правка «без изменений» возвращаются модели ошибкой, модель исправляется сама.
- **apply_patch.** Блок — «файл» `cards/<card_id>/<block_id>.md` (поле `path` в `get_card`).
  - Ханк — «найти фрагмент, заменить», а не сравнение строк: для блока-абзаца модель пишет в `-` кусок строки.
    Фрагмент должен встречаться ровно один раз; пробелы по краям прощаются.
  - База патча — ожидающая правка блока, если есть, иначе его текст (так «Переделать» продолжает её); это же
    сказано модели в протоколе и описании инструмента.
  - Патч **атомарный**: ошибка в любой секции — ничего не предлагается, модель получает все ошибки по путям.
  - `Add/Delete File`, `Move to` — ошибка с подсказкой (заполнить пустой блок — `edit_block`).
  - В истории custom-вызов хранится как обычный `toolCalls[i]` с `type: "custom"` (ввод — в `arguments`);
    `turn/input.ts` реплеит его парой `custom_tool_call` / `custom_tool_call_output` — DeepSeek проверяет тип пары.
  - Шаг на экране — по одному на блок патча (id `<вызов>:<карточка>:<блок>`), появляются по ходу стрима.
- Новая правка того же блока делает прошлую ожидающую `superseded`.
- Создавать, удалять и переименовывать блоки нельзя, но пустой блок можно заполнить.

**Пауза на `ask_user`.** Ход останавливается, в `state.pending` сохраняются вопросы и уже готовые
результаты остальных вызовов того же хода. Ответ (`POST /:id/answer`) дописывает tool-результаты всех
вызовов в порядке вызовов и продолжает тот же ход. Если вместо ответа пользователь пишет новое сообщение,
вопросы считаются пропущенными.

**Лимиты** — настройка чата (карточка «Лимиты хода» в настройках, `COAUTHOR_LIMITS`):
- `maxRounds` вызовов модели за запуск цикла (после ответа на вопросы — заново), последний — без инструментов,
  а править можно только прочитанную карточку, поэтому минимум 3 (прочитать, поправить, ответить); старые
  значения ниже минимума сервис поднимает до него;
- `maxEdits` правок блоков за сообщение пользователя — считаются **удачные** правки по истории (`turn/budget.ts`),
  патч на N блоков — N правок; от зацикливания на ошибках защищает лимит раундов;
- `maxQuestions` пауз на вопросы за сообщение;
- лимит веб-поиска — из настроек пользователя.

Модель знает лимиты числами (раздел `## Limits` протокола) и видит остаток: в каждый результат инструмента
дописываются `edits_left` и `rounds_left`. Исчерпанный лимит не прячет инструмент, а отвечает ошибкой с
объяснением — модель заканчивает ход и говорит пользователю, что осталось.

**Живой показ (`POST /:id/messages`, `/:id/answer` — SSE-поток):**
- Проверки (`busy`, `preset_required`, `no_cards`, нет ключа…) идут до потока и отвечают обычным JSON с кодом.
  Сам ход — в потоке, лок снимается в его конце.
- События (`SSE_EVENTS`):
  - `step` — шаг с `id` вызова: `cards` (`list_cards`, в старых чатах `get_cards`), `card` (`get_card`),
    `search`, `edit`; статус `running → done | failed`. У готовой правки в
    событии лежат все правки чата: новая могла заменить прошлую правку того же блока;
  - `token` — кусок текста ответа;
  - `reset` — модель перезапущена после сбоя, показанный текст и незавершённые шаги попытки стираются;
  - `ping` — раз в 15 с: раунд с мышлением молчит долго, а edge-nginx рвёт соединение без данных;
  - `done { chat }` — конец, полный чат; `error { code }` — ход упал, ничего не сохранено.
- Модель стримится всегда (`llm/responses/stream.ts`: текст и аргументы вызовов по дельтам, итог — из
  финального события `response.completed`). Шаг правки показывается, как только в неполных аргументах прочитались `card_id` и
  `block_id` (`turn/steps.ts`), а весь текст блока ещё пишется.
- Шаги завершённых ходов не хранятся: `turn/feed.ts` собирает их из вызовов в истории, на экране это свёрнутая
  строка «Ход работы · N шагов».
- Поток оборвался без `done`/`error` — ход на сервере идёт дальше. Клиент не возвращает текст в поле (иначе
  сообщение задвоится), а перечитывает чат и подхватывает ход опросом.

**Прочее:**
- `max_tokens` хода — не меньше 16000: `edit_block` несёт весь текст блока в аргументах, и с маленьким
  лимитом пресета JSON обрезался бы.
- **Рассуждение у вызовов текущего хода обязательно**: DeepSeek в режиме размышлений отвечает 400, если у
  вызова после последнего сообщения пользователя нет `reasoning` (проверено пробой). Поэтому оно
  сохраняется в `state` у текущего хода (нужно при продолжении после вопросов), у прошлых ходов
  выбрасывается при записи и не уходит модели. У синтетического `list_cards` — своё короткое рассуждение.
- Упавший ход не сохраняет ничего, клиент возвращает текст в поле ввода.

## Локи и подхват после обновления страницы

- **Лок чата** (`chat-lock.ts`) сериализует все записи в `state`: ход, ответ, решения, настройки,
  очистку. Ход держит лок целиком (десятки секунд). Пока лок взят, `GET` отдаёт `running: true`, и webapp
  опрашивает чат каждые 3 с (`useCoauthorChat`). Так страница, обновлённая посреди хода, подхватывает
  ответ.
- **Состояние идущего хода** (`turn-progress.ts`) — в памяти процесса: `GET` посреди хода отдаёт ленту и правки
  из него, а шаги — полем `liveSteps`. В БД ход попадает только в конце. Текст по кускам такая страница не видит,
  только шаги.
- **Ошибка упавшего хода** помнится 10 минут (`lastError`).
- **Принятие правки** (`POST /:id/review`) пишет блок в карточку через `CardsRepository.setCategoryContent`
  под `card-lock` (тот же лок, что у формы карточки и генерации).
  - Правка принимается, только если блок не меняли с момента предложения (`baseContent`). Иначе она
    возвращается в `stale` и остаётся ожидающей, чтобы не затереть чужие изменения.
  - Webapp видит такое состояние сам: текст блока ≠ `baseContent`.

## Экран

- **Телефон:** вкладки «Чат / Карточки».
- **ПК (≥ 62em):** чат слева, карточки колонкой справа.
- **Карточки:**
  - чипы персонажей со счётчиком ждущих правок и полоса «N правок ждут решения · Принять все»;
  - блок с правкой показывает пословный diff от `baseContent` (`lib/wordDiff.ts`) с переключателем
    «Изменения / Было / Стало»;
  - кнопки «Принять», «Переделать» (переключает на чат с черновиком просьбы) и ✕;
  - правка появляется в карточке сразу, как готова, а кнопки решений заблокированы до конца хода: ход ещё может её заменить.
- **Вопросы ИИ** — та же карусель, что у генерации карточек (`shared/components/AskUserQuestionsCarousel`).
- **Настройки чата:** карточки (в форме только выбранные, остальные — в шторке с поиском, `CardsField`), пресет, свой системный промпт со «Сбросить», тумблеры веб-поиска и картинок, лимиты хода, очистка переписки,
  удаление. Удаление чата карточки не трогает.
