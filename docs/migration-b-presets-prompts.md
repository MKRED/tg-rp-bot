# Миграция B — удаление промпт-полей из `generation_presets`

Вторая (завершающая) часть рефакторинга «Семплинг vs RP-шаблоны» (миграция A уже применена и
задеплоена — см. коммит `fedeca9`, `refactor(presets): выделить RP-шаблоны...`). Миграция A
создала `rp_templates` и перенесла в них данные промптов, но **не удаляла** старые поля из
`generation_presets` — специально, чтобы оставить окно отката. Эта миграция закрывает окно:
удаляет из `generation_presets` семь колонок, которые с миграции A код не читает и не пишет.

**Когда запускать:** по прямой просьбе пользователя со ссылкой на этот файл. Отдельного дедлайна
нет — чем дольше ждём, тем больше уверенности, что окно отката не понадобилось.

## Что именно удаляется

В `bot/src/db/schema.ts`, таблица `generationPresets` (сейчас строки ~154-200), блок под
комментарием `// ВРЕМЕННО — оставлены до миграции-дропа...` (строка 177):

- `systemPrompt` (`system_prompt`)
- `auxiliarySystemPrompt` (`auxiliary_system_prompt`)
- `postHistoryInstruction` (`post_history_instruction`)
- `userPersonaPrompt` (`user_persona_prompt`)
- `userPersonaStreaming` (`user_persona_streaming`)
- `translationSystemPrompt` (`translation_system_prompt`)
- `promptOrder` (`prompt_order`)

Данные не теряются: те же значения уже живут в `rp_templates` (перенесены миграцией A, 1:1 по
бывшему `generation_presets.id` через `chats.template_id`).

## Шаги

1. **Проверить, что окно отката не нужно.** Прод сейчас на коммите `fedeca9` или новее, работает
   штатно, чат/impersonate/перевод используют `rp_templates` без ошибок. Если сомнения есть —
   сначала разберитесь (`log-analyzer`/`bug-investigator`), не запускайте эту миграцию вслепую.

2. **Сузить схему.** В `bot/src/db/schema.ts` удалить семь полей выше из `generationPresets`
   (строки 177-189) вместе с комментарием «ВРЕМЕННО». Обновить docblock над таблицей (строки
   ~148-153) — убрать упоминание отложенного дропа, оставить только «источник сэмплинга,
   режимо-независим».

3. **`tsc`-сеть безопасности.** Сразу после правки schema.ts — `yarn build` (или хотя бы
   `yarn workspace bot build`). Сужение типа `GenerationPreset` обязано сломать компиляцию в
   любом месте, которое ещё читает `preset.systemPrompt`/`.promptOrder`/др. Если `tsc` чист —
   в коде не осталось скрытых читателей этих полей. Если упал — это баг, найденный сейчас, а не
   на проде; чинить перед тем, как продолжать (скорее всего значит, что миграция A на самом деле
   была неполной — стоит позвать `advisor`).

4. **Сгенерировать миграцию.** `yarn workspace bot drizzle-kit generate` — ожидаемый результат:
   один новый файл в `bot/drizzle/`, содержащий ровно семь `ALTER TABLE "generation_presets" DROP
   COLUMN ...`. Если генератор предлагает что-то ещё (другие таблицы, ALTER TYPE и т.п.) —
   остановиться и разобраться, откуда лишний diff, прежде чем применять.

5. **Ревью перед применением.** Позвать `advisor` с диффом schema.ts + сгенерированным SQL —
   короткая сверка «удаляем ровно то и только то», без сюрпризов. Это разовая проверка, не полный
   повтор ревью миграции A.

6. **Бэкап — по обстоятельствам.** В отличие от миграции A (чисто аддитивная, решили без бэкапа),
   это **разрушающая** операция — `DROP COLUMN` необратим на уровне БД. Дев-базы по-прежнему нет
   (единственный пользователь, прод и есть дев — см. план рефакторинга в
   `C:\Users\Михаил\.claude\plans\giggly-wishing-milner.md`, если ещё доступен). Раз данные
   дублированы в `rp_templates` и шаг 3 подтвердил отсутствие читателей — риск невелик, но:
   спросить пользователя, нужен ли `pg_dump` именно на этот раз (не делать бэкап молча-по-умолчанию
   и не пропускать его молча-по-умолчанию — решение пользователя, как и в прошлый раз).

7. **Применить.** `yarn workspace bot drizzle-kit migrate` — на единственной (продовой) БД, по
   туннелю.

8. **Проверить.** Ручная сверка: `SELECT * FROM generation_presets LIMIT 1` — семи полей больше
   нет; штатная работа приложения (создать/отредактировать пресет, отправить сообщение в RP-чате,
   impersonate, ИИ-перевод) — всё по-прежнему берёт промпты из `rp_templates`, семплинг из
   `generation_presets`, без регрессий.

9. **Гейт + деплой.** `test-runner` (yarn test + yarn build) → коммит
   (`refactor(presets): удалить промпт-поля из generation_presets (миграция B)`) → пуш в `main` →
   деплой по стандартной процедуре из CLAUDE.md (сначала `drizzle-kit migrate` на проде — шаг 7
   уже сделан, — потом код можно катить в любом порядке, поскольку сужение схемы код не ломает
   обратной зависимостью; но для чистоты держаться обычного порядка «код после миграции»).
